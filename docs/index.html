Where should the SRE agent run?

Three ways to run an LLM (large language model) SRE (site reliability engineering) agent from Splunk's AI Toolkit were built and tested on the TukTukPay EC2 (Elastic Compute Cloud) Splunk against live failure scenarios. One runs the agent we wrote, with Claude Opus 5.5, from a single line of SPL (Search Processing Language).

New on 28 Oct: five detection modules that cover what ECOD misses, and the whole agent as a public GitHub repository with a step-by-step quick start.

Recommended

Own agent in a toolkit container

Our sre_agent runs inside the AI Toolkit's container framework on our EC2. Splunk starts it with | fit AITKContainer. Full control: Claude Sonnet / Opus 5.5 with thinking, our loop, budgets and approval rules.

Proven live: Act 1 correct in 74 s, USD (US dollars) 0.33.

How option C works

The AI Toolkit includes the Data Science and Deep Learning (DSDL) container framework. Splunk's container image runs a small web API (application programming interface); the toolkit sends the rows of a search to it over HTTPS (Hypertext Transfer Protocol Secure) and the image's API loads a Python module, app/model/<algo>.py, and calls its apply(). That module does not have to be machine learning. Ours hands each alert row to the agent and returns its answer as columns.

What we built

  • services/sre-agent/aitk-container/Dockerfile: Splunk's mltk-container-golden-cpu:5.2.1 + Python 3.11 + Anthropic SDK + sre_agent.
  • tuktuk_sre.py: the toolkit module (init, fit, save, load, summary, apply).
  • aitk_runner.py: one agent case per row, policy ask (proposes, never acts).
  • Toolkit config: model stanza tuktuk_sre → https://localhost:5000, Docker connection, shared API token in Splunk's password store.

Why Claude 5.5 fails inside Launchpad

"Thinking" is Claude's extended reasoning: a private scratchpad before each answer or tool call. Splunk's cloud runtime always sends thinking: {"type": "disabled"}. Sonnet 4.5 accepts that. The 5.5 models changed the options and refuse the old value, so every run fails with HTTP 400 even though the connection test passes, because the test runs on the EC2 instance and not in the runtime. Errors as recorded in Splunk's audit log on 27 Oct:

Sonnet 5.5  400  To turn thinking off on this model, send "thinking": {"type": "between_tools"}
                 instead of {"type": "disabled"}.
Opus 5.5    400  "thinking.type.disabled" is not supported for this model.
                 Use "thinking.type.adaptive" and "output_config.effort".
Two traps for anyone repeating this. An Anthropic connection keeps its endpoint only if it is set when the connection is created; editing it later drops the endpoint and runs fail with "Connection error". Agent names must be letters and digits only; a hyphen gives a bare "Failed to create agent" in the UI (user interface), with the real reason only in mlspl.log.

Does the hypothesis tree help?

Datadog's Bits AI SRE investigates as a hypothesis tree: competing causes, each validated, invalidated or inconclusive, with deeper "why?" branches under the ones that hold. We gave the Launchpad agent the same method and ran it against the existing checklist instructions on the same model (Claude Sonnet 4.5), the same incident and the same moment.

A tree is worth keeping only with that freshness check enforced in code, plus parallel branches and per-branch budgets, which only option C can provide. Single runs per act, so treat the timing differences as indicative.

Sub-agent hypothesis tree in our agent

The Launchpad test showed the limit of a tree written into instructions: one model explores every branch in turn, and nothing stops it from accepting a branch built on old evidence. In option C the loop is our code, so the tree can be built properly. Since 27 Oct our agent has a second investigation method, SRE_AGENT_METHOD=tree. The default single loop is unchanged.

Inside one sub-agent

Each hypothesis gets its own sub-agent: a separate Claude conversation with its own tools and budget, started in its own thread. It knows only its hypothesis, the path above it in the tree, the alert and the evidence bundle. It never sees what the other sub-agents are doing, so one branch cannot talk the others into its answer.

Results: concurrency proven, accuracy not better

Verdict. The tree works as designed (parallel sub-agents, code checks, deeper branches) but did not beat the single loop: 7 of 9 offline against 9 of 9, wrong on the live trap where the loop was right, and about twice the cost and time. The freshness check trusts the time the sub-agent reports for "last seen"; the leftover crash errors fell inside its 5-minute window. The single loop stays the default in the container (SRE_AGENT_METHOD=loop); the tree stays available per call with method="tree". Next step before trying again: measure "last seen" by code (a Splunk search per cited event), not from the sub-agent's answer.

What starts the agent

Two alerts can start an investigation. The detector alert reacts when an Observability Cloud detector crosses a fixed threshold. The ML anomaly alert uses three AI Toolkit DensityFunction models that learned normal behaviour per service from 330 quiet minutes, and fires on what is unusual for that service.

Anomaly detection that starts the agent: tested on every act

The alert "TukTukPay - ML anomaly runs TukTukPaySRE" scores every service every 2 minutes with AI Toolkit models and starts the agent when something is unusual. Which models, and which combination

Every candidate was trained on the same clean minutes with the same false-alarm budget (99.5th percentile of its own scores), then scored on the 8 acts and 1,019 quiet minutes. Detection is easy here: all of them caught 8 of 8 in about 37 s. The difference is false alarms, and whether the alert names the right service.

What ECOD is

Empirical-Cumulative-distribution-based Outlier Detection (PyOD). For each signal of a service it learns the normal distribution from quiet minutes, scores how far into the tail a new value is, and adds the surprise across signals. No parameters to tune, under a second to train, and it shows which signal drove the score. It judges signals independently and has no sense of time of day, so a longer baseline matters.

The toolkit's own DSDL notebooks are examples rather than detectors (one-feature ECOD with a broken reload; a random cut forest that always flags 1 %; an untuned autoencoder). The useful part is PyOD, scikit-learn and TensorFlow inside the same image.

Covering what ECOD misses: five detection modules

ECOD judges every minute on its own and every signal separately. That is why it is good at sudden faults, and it is also why it misses slow faults, faults that depend on the time of day, faults that appear only in a combination of signals, and faults where the data simply stops. On 28 Oct we listed 14 such cases and wrote five detectors as AI (artificial intelligence) Toolkit container modules in one image (based on Splunk's CPU (central processing unit) image, which already has PyOD, scikit-learn and statsmodels). Each module learns one model per service and returns the same three columns per minute and service: score, flag and reason, so one alert can combine them.

Offline test in the container image with no network (28 Oct): 2 days of synthetic baseline with a daily traffic curve to train, 1 day with the 11 faults injected, and 1 clean day. Result: pass. One of the intended modules caught every fault, no module raised a false alarm on the clean day, and a single harmless warning on a quiet service raised nothing. IF = Isolation Forest.

What we learned tuning them

  • A 99.5th-percentile threshold flags about 0.5 % of minutes by construction: ECOD gave 26 false-alarm episodes a day. The 99.9th percentile plus 2 minutes in a row brought that to 0.
  • CUSUM (cumulative sum) drifts on sparse counts, so the drift module watches only continuous signals (latency, memory, error %).
  • When logs decouple from traffic, every signal is normal on its own. Neither ECOD nor Isolation Forest caught it; the seasonal and drift modules did.
  • The rules need a minimum size (5 errors, or a significant share). Without it, one warning on a service that normally has zero errors would start an investigation, which is the overnight false alarm the live alert produced.

Still open

  • Not yet live. The modules have been tested only on synthetic data. Next: run the container beside the agent container, train on real quiet hours, create the new alert disabled, replay the acts, then switch over and retire the three DensityFunction models.
  • Planned changes (deploys, load tests) need suppression windows in the alert.
  • Daily and weekly patterns need weeks of history for Prophet. Until then, an hour-of-day baseline.
  • Faults outside these signals, such as a partner outage that shows only as declines, still need Observability Cloud detectors and service-level objectives.

TukTukPay SRE Agent app in Splunk

Our container agent's investigations are not in Launchpad's run history, so a Splunk app shows them, read live from index=tuktukpay_agent_audit: a fleet strip, the case list, a conclusion card (root cause, impact, recommended action waiting for approval, confidence band with its basis, tokens and cost), and tabs for the hypothesis tree (tree on the left, the selected hypothesis on the right: what the sub-agent said, what code decided, evidence with links to Splunk and Observability Cloud, what was checked), the sub-agent timeline, evidence, the agent trace and the narrative. Version 1.3.0, at /en-US/app/tuktukpay_sre_agent/cases on the EC2 Splunk. The workshop guest tuktuk_guest can read it, limited to the event types the app uses.

Get it: public repository and quick start

Everything above that is not tied to the lab is in github.com/khsydney/splunk-aitk-launchpad-sre-agent: the Launchpad agent set-up, the container agent, the five detection modules, the SRE Agent app, and this page (published at khsydney.github.io/splunk-aitk-launchpad-sre-agent). Before it was published, host names, addresses, account and organisation IDs, credentials, customer names and personal names were removed. The lab scripts are kept under research/.

The quick start is a set of numbered Python scripts (standard library only) that run from a laptop against Splunk Web's REST (representational state transfer) API. One config.env file drives them. Each script checks its own result, prints the fix when something is wrong, and is safe to re-run.

Tested end to end on 28 Oct against the EC2 Splunk 10.6 with AI Toolkit 6.2. Steps 0–4 passed: the test agent answered a health check in 56 s with live numbers and no failed tool calls, and the detector alert found 80 detector alert events. Step 5 trained its three models (1,187, 1,186 and 725 minutes; 10, 10 and 7 services) and saved its alert. Every test object was deleted afterwards. Two bugs found during the test were fixed before publishing: the log query got search prepended twice, and long training searches broke the job polling.

Recommendation

  1. Production path: option C. Run the SRE agent in the toolkit container and start it from the ML anomaly alert and the detector alert with | fit AITKContainer / | apply tuktuk_sre. It is the only option that runs Claude 5.5 with thinking and keeps our approval rules, budgets and evidence check. Write its answers to an index so a dashboard shows them.
  2. Workshop story: show A and C together. Launchpad with Claude Sonnet 4.5 and the checklist instructions is the product as the customer would get it; the container agent shows how far a customer can take it with their own agent, model and governance, still started from Splunk.
  3. Keep the checklist instructions in Launchpad. The tree did not beat them there and failed once on stale evidence. The code-checked tree with parallel sub-agents is now built into our agent (see Sub-agent hypothesis tree); tested on 27 Oct, it was less accurate than the single loop (7/9 offline, wrong on the Act 7 → 4b trap) at twice the cost, so the single loop stays the default. Retry only after "last seen" is measured by code.
  4. Drop option B for now. Revisit only if Splunk confirms custom LLM connections for Launchpad agents; it would also need a public endpoint restricted to the runtime's address.
  5. Detection: replace the per-signal alert with the five modules (ECOD for sudden faults, drift, seasonal and rules for what ECOD misses, Isolation Forest kept as a second opinion) plus the call-graph ranker; train on clean real hours; fix the throttle (marker at start, per fault). The modules passed the offline coverage test (see above); re-run all acts live before switching over.
  6. Report to the AI Toolkit team: the runtime's fixed thinking: disabled blocks current Claude models; the "Run AI Agent" alert action never passes alert fields to the agent.
